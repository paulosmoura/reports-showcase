Como publicar o dashboard online para vários clientes

Este documento separa o que pode ser feito com o relatório atual e o que precisa mudar para vender acesso a clientes com autenticação real, isolamento de dados e custo mensal previsível.

Diagnóstico do relatório atual

O dashboard publicado hoje é um site estático: HTML, CSS, JavaScript e um arquivo de dados ficam disponíveis no navegador. A tela de login atual serve como barreira visual, mas não protege de fato os dados contra alguém que inspecione o código ou baixe os arquivos do repositório/site.

Decisão importante: para clientes pagantes ou dados confidenciais, não use GitHub Pages com senha em JavaScript como controle de acesso principal. O correto é ter autenticação no servidor/backend e dados filtrados por cliente antes de chegar ao navegador.

Arquitetura recomendada

  1. Frontend
    Publicar a interface do dashboard em Vercel, Cloudflare Pages ou GitHub Pages.
  2. Login real
    Usar Supabase Auth, Auth0, Clerk ou Firebase Auth. Para este caso, Supabase encaixa bem porque já entrega Auth + banco Postgres.
  3. Multi-cliente
    Adicionar `client_id` aos dados e regras de acesso. Cada usuário só enxerga dados do próprio cliente.
  4. Banco e políticas
    Mover `report_data.js` para Postgres/API e aplicar Row Level Security. O navegador nunca deve receber dados de outros clientes.
  5. Operação
    Criar painel administrativo para cadastrar clientes, usuários e atualizar planilhas/relatórios.

Recomendação direta

MVP de produção

Para começar vendendo acesso com baixo custo, use:

  • Cloudflare Pages ou Vercel para hospedar a interface.
  • Supabase Pro para autenticação, banco, backups e políticas por cliente.
  • Domínio próprio como `dash.dna365.com.br`.
  • Subdomínios ou filtros por cliente, por exemplo `cliente-a.dna365.com.br` ou login único com seleção automática.
Custo inicial saudável: comece mirando US$ 25 a US$ 45/mês antes de gastar com infraestrutura maior.

Cenário maior: 2.000 clientes

Para 2.000 clientes, o ponto crítico deixa de ser somente hospedagem e passa a ser arquitetura multi-tenant, governança de acesso, volume de dados, suporte e observabilidade. A recomendação é usar poucos ambientes compartilhados bem isolados, e não criar uma infraestrutura separada para cada cliente.

Não recomendado: criar 2.000 projetos Supabase, 2.000 bancos ou 2.000 sites separados. Mesmo que funcione tecnicamente, a operação, backups, deploys e custos ficam difíceis de controlar.

Arquitetura recomendada para 2.000 clientes

  • Multi-tenant pooled: uma aplicação única, usuários em uma tabela de organizações/clientes e todos os dados com `client_id` obrigatório.
  • RLS no banco: Row Level Security para garantir que cada cliente veja somente os próprios registros.
  • Sharding quando necessário: começar com um banco principal e separar por região, porte ou contrato quando o volume crescer.
  • Clientes enterprise dedicados: apenas clientes grandes ou com exigência contratual ficam em banco/projeto separado.
  • Cache e pré-agregação: indicadores pesados devem ser pré-calculados; o dashboard não deve recalcular tudo a cada acesso.
  • Fila de processamento: uploads de planilha e geração de métricas devem rodar em background, com status e logs.

Regras para vários clientes

  • Cada registro de amostra, ativo, navio ou indicador deve ter um `client_id`.
  • Cada usuário deve pertencer a um ou mais clientes.
  • Admins DNA365 podem ver tudo; clientes só veem seus próprios dados.
  • Exportações CSV/Excel também precisam respeitar o filtro do cliente.
  • Backups e logs devem ser habilitados antes de vender acesso recorrente.
  • O repositório público não deve conter planilhas brutas nem dados privados.

Plano de implantação sugerido

Fase Entrega Resultado
Fase 1 Manter o dashboard visual atual, mas colocar login real e banco por cliente. MVP seguro para primeiros clientes.
Fase 2 Criar painel admin para cadastrar cliente, usuário e carregar dados. Operação sem depender de editar código a cada cliente.
Fase 3 Automatizar atualização do relatório, logs, alertas e faturamento por cliente. Produto SaaS mais escalável.

Fontes de preço consultadas

  • GitHub Pages: disponível para repositórios públicos no GitHub Free, mas a própria documentação limita o uso para SaaS/comercial sensível: GitHub Pages limits.
  • Vercel: plano Pro anunciado a partir de US$ 20/mês, com limites e uso adicional por métrica: Vercel Pricing.
  • Supabase: Pro a US$ 25/mês, 100K MAUs incluídos, 8 GB de banco por projeto, 250 GB de bandwidth e backups diários: Supabase Pricing.
  • Cloudflare Workers: plano pago com cobrança mínima de US$ 5/mês para Workers/Pages Functions e recursos de edge: Cloudflare Workers Pricing.
  • Câmbio aproximado usado: 1 USD = R$ 5,04, referência Forbes Advisor em 22/05/2026: USD/BRL Forbes Advisor.
